Build status (v0.7.2, 23 Nov 2026). This is the original engine specification. The engine has since been built to run Hearthblock Online, a classic fantasy MMORPG, and some parts were built differently:
  • Content as data: all content (rules, textures, sounds, fonts, models, rigs, animation, shapes, UI words) is a data pack the server streams; the player client hearthblock carries none. Luau scripting is not built yet; game rules are Rust.
  • One world: no realms; the world shards itself per area, keeps parties together, phases content per player, and runs across a cluster of instances joined by a Raft quorum.
  • Transport: WebSocket over TCP (not QUIC), so it works through HTTPS tunnels.
  • Movement: the client moves and the server checks it; server-simulated movement is planned after world streaming, which is in progress.
  • Releases: one signing key, two programs (dyno and hearthblock), self-updating.
How it is actually built: Hearthblock Online architecture (also docs/architecture.md in the repository).

Dyno: a live, script-defined multiplayer 3D engine

Dyno is a native engine for multiplayer block worlds and 3D worlds. All game logic is Luau code and data records in one content store on the server. Developers change a running game. Connected players receive the change without a restart or a rejoin.

The engine is built for agent-first development: AI agents and humans use the same typed, headless APIs (section 27).

The first benchmark is Hearthblock: a working Minecraft-class survival game that people join over the internet.

3. Goals and non-goals

Goals

  • All game logic is Luau. The engine contains no gameplay. Standard gameplay helpers ship as the Luau pack std.
  • Agents are developers too. Every tool action has a typed, headless API with data as the result (section 27).
  • Third parties can add content as packs, without changes to other packs.
  • All game content is records in one versioned content store.
  • A developer can change any record while players are connected.
  • One server process is the authority for all world state.
  • Block worlds are built in. Scene worlds follow in v1.2.
  • The visual quality matches Minecraft, Roblox and classic MMOs: stylised art, pixel textures, good lighting.

Non-goals

  • Photoreal rendering, PBR authoring, ray tracing.
  • Peer-to-peer or client-authoritative multiplayer.
  • One world across many server processes.
  • Marketplace, avatar economy, platform accounts. Authentication is a plug-in interface.
  • Mobile, console and browser clients in v1. The core must not use desktop-only APIs.
  • Native code written by game developers. Only first-party native plugins exist.

7. Content store

7.1 Records and IDs

  • A record ID has the form namespace:name. Both parts use a-z, 0-9, _ and /.
  • Reserved namespaces: engine (engine), tex, mdl, snd (assets). Each place declares its own game namespaces, for example hearth.
  • A record is required by @content/namespace/name. Example: require("@content/hearth/components/hunger").
  • Record kinds: block, item, template, component, recipe, sound, material, model, animation, particle, loot, biome, tag, patch, locale, test, module, ui, asset, role, config.
  • The record ID maps to the sync path: hearth:blocks/emberstone is hearth/blocks/emberstone.luau (TOOL-001).

The source text of a record is canonical. For a definition, the store parses the source into a derived view: static fields and handlers. Tools read and patch the view. The store applies each patch to the source text, so comments and formatting stay unchanged.

7.2 Transactions

Transaction states: submitted → validated → (proposed → approved, for agent transactions on live places, AGT-043) → prepared → active, or rejected or aborted. Section 8 specifies the prepare and activate steps.

IDRequirementVerifyMS
STORE-010A transaction must list every record it reads and writes, with the base version of each.TestM0
STORE-011If a written record changed after its base version, the store must merge per field and per handler. If the same field or handler changed, the store must reject the transaction with E_CONFLICT.TestM0
STORE-012The store must parse and strict-typecheck the merged result. It must return all errors, not only the first. If any error exists, the store must reject the transaction and keep the current version active.TestM0
STORE-013The store must stage the new modules on the server and run their init. If init fails, the store must reject the transaction.TestM0
STORE-014The store must activate one transaction at a time. Later transactions wait in a queue.TestM0
STORE-015Each validated transaction must receive the next candidate version. The store version becomes that number at activation. History must show an aborted candidate version as aborted.TestM0
STORE-016The store must be an append-only op log with a store checkpoint every 100 versions.TestM0

20.6 Development loop: build and verification speed

There are three loops. Each has a time budget.

  • Content loop (game developers): edit Luau, typecheck, test, apply live. No Rust compilation.
  • Engine loop (engine developers): edit Rust, rebuild, run, test.

Facts about other engines were checked on 22 November 2026 and can change. Dyno does not compete with these engines on general features. It competes on one feature they do not have: safe changes to a running multiplayer game, code and data together.

What Dyno takes

  • Bevy: archetype ECS, explicit system order, change detection, plugins.
  • Unity: data assets, prefabs and variants (templates), the inspector.
  • Unreal: replication conditions, relevancy and priority. Live Coding shows that patching compiled code is fragile.
  • Roblox: Luau, one binary for play and edit, a tree that new users understand.
  • Minecraft: string-keyed registries, paletted chunks, data packs and reload.

Where Dyno is weaker

  • Gameplay speed: Luau is slower than native code. Bulk APIs and native codegen reduce the gap.
  • Rendering: far below Unreal and Unity. This is accepted for a block game.
  • Tools: Studio is limited to the content workflow in v1.
  • Prediction: limited to movement and block actions, tested from M2.
  • Ecosystem: no asset store. Standard formats reduce the cost.
